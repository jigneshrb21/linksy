# Linksy 🔗

A production-style URL shortener built with Spring Boot, JPA/Hibernate, and PostgreSQL — deployed live on Render, backed by Supabase.

**Live app:** https://linksy-d9af.onrender.com

---

## Overview

Linksy takes a long URL and returns a short, unique code that redirects to the original destination. It's a small project, but it's built the way a real backend service is built: layered architecture, proper validation, centralized error handling, environment-based configuration, containerized deployment, and a real managed database — not a toy script.

## Tech Stack

- **Java 25**, **Spring Boot 4.1**
- **Spring Data JPA + Hibernate** — ORM and persistence
- **PostgreSQL** (Supabase, managed, free tier) — production database
- **H2** (in-memory) — local development fallback, zero setup required
- **Docker** — multi-stage build for deployment
- **Render** — hosting (free tier, containerized deployment)
- **JUnit 5** — unit testing
- **Maven** — build tool

## Architecture

```
Client
  │
  ▼
LinksyController        (@RestController — HTTP layer, request/response)
  │
  ▼
LinksyService            (@Service — business logic)
  │
  ▼
UrlMappingRepository      (JpaRepository — data access, zero implementation code)
  │
  ▼
PostgreSQL (Supabase)
```

Cross-cutting:
- **GlobalExceptionHandler** (`@RestControllerAdvice`) — catches exceptions from any layer and returns clean, safe JSON error responses instead of stack traces.
- **Base62Encoder** — a stateless utility used by the service layer to turn a numeric database ID into a short alphanumeric code.

## API Endpoints

| Method | Endpoint | Description |
|---|---|---|
| `POST` | `/api/shorten` | Accepts `{ "originalUrl": "..." }`, returns `{ "shortUrl": "..." }` |
| `GET` | `/{shortCode}` | Redirects (HTTP 302) to the original URL |

**Example:**
```bash
curl -X POST https://linksy-d9af.onrender.com/api/shorten \
  -H "Content-Type: application/json" \
  -d '{"originalUrl": "https://example.com/some/long/path"}'

# → { "shortUrl": "https://linksy-d9af.onrender.com/1" }
```

## Design Decisions

**Why Base62 encoding instead of random strings?**
Short codes are generated by Base62-encoding the database's auto-incrementing primary key, rather than generating a random string and checking for collisions. Since the ID is already guaranteed unique by the database, collisions are structurally impossible — no need for a "generate, check, retry" loop. The trade-off is that codes are sequential and technically guessable in order, which is an acceptable trade-off for this scale but worth knowing as a limitation (a production system serving sensitive links might prefer random codes with a collision check, or a hybrid like a Snowflake ID).

**Why two database writes per shorten request?**
The flow is: insert the row (to get an auto-generated ID from the database) → encode that ID → update the row with the resulting short code. This means `shortenUrl()` does an INSERT followed by an UPDATE. The alternative — pre-generating an ID before insert — would need a distributed ID generator. For this project's scale, two writes on the (infrequent) creation path is a reasonable trade-off, especially since redirects (reads) happen far more often than shortens (writes).

**Why Spring Data JPA over Spring JDBC?**
JPA/Hibernate auto-generates the SQL for standard CRUD and query-derivation methods (`findByShortCode`), which keeps the repository layer to a single-line interface with zero implementation. Spring JDBC (`JdbcTemplate`) requires writing and maintaining raw SQL and manual `ResultSet`-to-object mapping. For a single, simple entity with no complex relationships, JPA is the faster and cleaner choice; JDBC becomes more attractive when queries get complex enough that hand-tuned SQL and full control matter more than convenience.

**Why environment-variable-based configuration?**
Both the database connection (`DB_URL`, `DB_USERNAME`, `DB_PASSWORD`) and the app's own public URL (`APP_BASE_URL`) are read from environment variables with local-safe defaults, e.g.:
```properties
spring.datasource.url=${DB_URL:jdbc:h2:mem:linksy}
app.base-url=${APP_BASE_URL:http://localhost:8080}
```
This means the exact same code runs locally against an in-memory H2 database and in production against real Postgres, with no code changes — only environment variables differ between environments. No credentials are ever committed to source control.

**Why HTTP 302 instead of 301 for redirects?**
`302 Found` (temporary redirect) is used instead of `301 Moved Permanently`. A 301 tells browsers to cache the redirect indefinitely, which would break the ability to ever change or expire a short link's destination later. 302 keeps every redirect going through the server, which matters for accurate click-count tracking too.

**Why separate DTOs instead of exposing the JPA entity directly?**
The `ShortenRequest` DTO — not the `UrlMapping` entity — is what the controller accepts as a request body. This prevents a client from ever supplying values for fields like `shortCode`, `clickCount`, or `id` directly in a request; those are entirely controlled server-side.

## Error Handling

All errors return structured JSON, never a raw stack trace:

| Scenario | Status | Response |
|---|---|---|
| Blank/invalid `originalUrl` | `400` | `{ "error": "originalUrl must not be blank" }` |
| Unknown short code | `404` | `{ "error": "Short code not found: xyz" }` |
| Unexpected server error | `500` | `{ "error": "An unexpected error occurred. Please try again later." }` |

Unexpected errors are logged server-side (via SLF4J) with full detail for debugging, while the client only ever sees a safe, generic message.

## Running Locally

```bash
git clone https://github.com/jigneshrb21/linksy.git
cd linksy
./mvnw spring-boot:run
```
No database setup required — the app defaults to an in-memory H2 database when no `DB_URL` environment variable is set. It'll be running at `http://localhost:8080`.

To run against a real Postgres instance instead, set the environment variables before running:
```bash
export DB_URL=jdbc:postgresql://<host>:5432/<db>
export DB_USERNAME=<username>
export DB_PASSWORD=<password>
```

## Running Tests

```bash
./mvnw test
```

## Deployment

Deployed on **Render** as a Docker container, built via a multi-stage `Dockerfile` (build stage compiles the jar, runtime stage runs it on a lean JRE-only image). Database is a managed **Supabase PostgreSQL** instance, connected via Supabase's **session pooler** rather than the direct connection endpoint.

Environment variables (`DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, `APP_BASE_URL`) are configured directly in Render's dashboard — never committed to the repository.

## Challenges Faced

**Docker build failing with `Permission denied` on `mvnw`**
The Maven wrapper script lost its Unix execute permission when committed from a Windows machine, causing the Docker build to fail with exit code 126. Fixed by explicitly running `chmod +x mvnw` as a build step in the Dockerfile before invoking it.

**`Network unreachable` connecting to Supabase from Render**
Supabase's direct database connection (`db.<ref>.supabase.co`) resolves to an IPv6-only address by default. Render's network doesn't support outbound IPv6, so every connection attempt failed at the socket level before authentication was even reached. The fix was switching to Supabase's **session pooler** endpoint, which is reachable over IPv4 — this required updating the connection URL, and importantly, the *username format* (the pooler requires `postgres.<project-ref>` rather than just `postgres`), since the pooler needs to know which project to route the connection to.

**Local URL leaking into production responses**
Early on, the base URL used to build the `shortUrl` response was hardcoded (`http://localhost:8080`), which would have returned the wrong domain once deployed. Fixed by moving it into an environment-variable-backed property (`app.base-url`), read via `@Value` in the controller — matching the same pattern already used for database configuration.

## What I'd Add With More Time

- Redis caching on the redirect path (`shortCode → originalUrl`) to reduce database load on reads, which are far more frequent than writes
- Rate limiting on `/api/shorten` to prevent abuse
- Flyway/Liquibase migrations instead of `spring.jpa.hibernate.ddl-auto=update`, which is convenient for a solo project but not something I'd use on a real team codebase
- A minimal frontend (single form + result display) for a non-technical demo
- Custom expiry dates and alias support (the `expiryDate` field already exists on the entity but isn't enforced yet)
